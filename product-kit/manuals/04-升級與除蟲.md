# 升級與除蟲

## 每次升級固定流程

1. 建立問題或需求紀錄，寫清楚預期結果。
2. 只在本機與 v2-test 修改。
3. 跑 `npm test` 與 `git diff --check`。
4. 檢查客戶端、業主端與 Pages 鏡像一致。
5. 遠端變更前重新備份目標 D1。
6. 核對環境名稱，取得當次部署／D1 寫入授權。
7. 先部署 Worker，再確認 health；需要時才部署 Pages。
8. 以真實流程驗收，不只看 HTTP 200。
9. 記錄版本 ID、Pages 部署代號、備份檔與驗收證據。

## 除蟲資料最少要有

- 發生日期與台北時間
- 標準版或旗艦版
- 客戶端、業主端或平台端
- 操作步驟與預期結果
- 實際畫面或錯誤文字
- booking／notification ID（若有；不要提供 LINE user ID）

## 通知重複的檢查方式

1. 先唯讀查詢同一 booking、template code 的通知筆數、`created_at`、`status` 與 `sent_at`。
2. 多筆不同 notification ID 表示系統建立了多筆，不可誤判為 LINE 自行重送。
3. 新通知建立必須有短時間後端去重，前端按鈕鎖定只能作為第一層保護。
4. `queued` 只能說「已排入傳送」；只有 `sent_at` 有值才可說已送出。
5. 已為 `sent` 的 LINE 訊息無法撤回，不可把資料庫紀錄偽改成 `cancelled`。

## 題庫載入錯誤的檢查方式

- 每項服務可分別指定題庫；`none` 代表該服務不使用評估，不是錯誤代碼。
- 業主題庫清單必須略過 `none`、空白與未知代碼，不能讓其中一項中斷整批載入。
- 題庫內容、LINE 客服知識庫與 AI 客戶訊息草稿是三套不同資料，不可混用。

## 禁止的快速修法

- 不直接改 production 試運氣。
- 不直接刪資料或重跑 migration。
- 不使用舊部署授權做新部署。
- 不把五分鐘 cron 當成新通知的主要發送機制。
- 不在 log、文件或截圖中留下 secrets。

## 回復策略

若新版本異常，先停止後續寫入並保存證據。依 Cloudflare 版本與部署紀錄回復應用程式；D1 只有在確認資料確實受損、備份可用且取得明確授權後才還原。
