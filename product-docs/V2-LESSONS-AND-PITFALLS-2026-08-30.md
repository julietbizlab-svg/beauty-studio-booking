# Beauty Studio Booking v2｜乾淨整合與 AI 預約助手踩坑紀錄

日期：2026-08-30（Asia/Taipei）

## 1. `git status --short` 的未追蹤計數有兩種口徑

預設 `git status --short` 可能把整個未追蹤目錄計成一筆；`--untracked-files=all` 則逐檔列出。兩者不可混用來判定批次是否漂移。整合腳本與驗收紀錄必須明寫採用哪個口徑，並同時核對完整檔案清單。

## 2. 批次腳本「全綠」仍要獨立複驗

曾遇到批次已由終端自行完成，不能因為看見綠色終點就重跑，也不能只引用腳本產物。正確作法是用獨立 `cmp`、SHA、基線、禁止項目與 `git diff --check` 複驗，避免重跑覆蓋現場。

## 3. 鏡像驗證必須先排除明確禁止檔

`.DS_Store`、安裝包與其他排除目錄會讓全目錄比較出現假差異。第 7 批驗證應先套用與搬移規則完全相同的排除條件，再比較來源與目的結構。

## 4. `git ls-files` 相同不代表工作內容已鏡像

追蹤檔清單只反映 HEAD；新搬入的未追蹤檔、已修改內容及禁止檔仍需另外核對。必須搭配 `status -uall`、來源 manifest、逐檔 `cmp` 與 SHA。

## 5. 產品來源與部署來源不可混為一談

A 是舊主目錄、B 是 v2-test 比對來源、C 是候選整合 worktree。即使某份文件或前端在 A 看起來正確，也不能假設它在線上；所有結論都要標示來源目錄、分支與部署狀態。

## 6. PR 建立成功不能只看提交動作回傳

GitHub 建立 PR 時曾同時出現錯誤提示，但實際已導航到 `/pull/3`。外部操作後應以 PR URL、標題、base／compare、commit 數與 Draft 標記作權威驗證，不能只信 toast 或按鈕回應。

## 7. 瀏覽器已登入不代表自動接管一定順利

Chrome 已登入 GitHub，但接管既有分頁曾逾時。安全恢復方式是保留原頁、不重複提交，重新建立同一登入 profile 的受控分頁，再從可見 DOM 確認表單。不可嘗試讀取 cookie、密碼或用腳本繞過登入。

## 8. Draft PR 建立與 merge／deploy 是三個不同授權

建立 Draft PR 只授權建立審查入口，不包含合併、部署或遠端資料變更。每個外部副作用都要依當次明確授權執行。

## 9. AI「已完成評估」不能只等同 `approved`

客戶觀點的「我已經做過評估」可能是填寫中、已送出待審或已核准。若舊對話 SOP 只在 `approved` 才退出，就會重複問卷。新版評估一旦存在，舊 SOP 應停止攔截，後續由新版頁面及人工審核狀態接手。

## 10. 修正重複評估時不可順便放寬預約門檻

停止重複問卷不代表可以跳過人工審核。應分開處理兩件事：對話路由退出舊 SOP；建立預約仍由既有 `approved`／免評估規則把關。

## 11. 舊 session 不宜為了「關閉」而擅自刪除

舊評估可能包含稽核、客戶答案或人工處理線索。修正採取「不再攔截、資料保留」，不執行刪除或未定義的狀態轉換，避免破壞歷史資料及 migration 約束。

## 12. AI 是否聰明應以預約完成度驗收

不能只測模型有回答。旗艦版 AI 應以「理解需求、只補必要資訊、不重複詢問、提供一個明確下一步、接回服務／日期／時段、必要時轉真人」作為驗收標準；最終衡量是客戶能否以最少來回完成有效預約。
