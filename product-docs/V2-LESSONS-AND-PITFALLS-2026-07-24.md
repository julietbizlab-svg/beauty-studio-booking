# Beauty Studio Booking v2｜踩坑與處理紀錄

日期：2026-07-24

## 1. 問卷原本放錯流程位置

### 問題

最初問卷只出現在「我的預約」裡，客人可先直接送出申請，之後才補資料。這與「建立申請前先詢問健康史」的產品需求不一致，標準版尤其明顯。

### 處理

- v2 客戶按下確認預約後，先開啟審核問卷。
- 手術史與疾病史／用藥必填。
- 問卷完成後才建立預約申請。
- Demo v1 保持原流程，避免誤傷舊版。

### 後續注意

若建立預約成功但問卷 API 或照片上傳失敗，不可再次建立重複預約；前端會切換成既有預約補件模式。

## 2. 補答與補照片資料互相覆蓋

### 問題

同一個 upsert 同時寫照片需求與問題需求；若只更新其中一組，未指定的另一組會被預設值清空。

### 處理

更新前先讀取既有 intake，只覆寫本次 payload 明確指定的欄位，保留另一組資料。

### 測試

已加入回歸測試，確認先要求照片、再要求補答時，照片需求仍保留。

## 3. 客戶端出現內部測試字樣

### 問題

驗收輸入資料含 `v2-test`、`端到端驗收資料` 等文字，直接顯示給客人；頁首也曾出現「客戶端、旗艦版、含 AI」等內部識別。

### 處理

- 移除客戶端角色與方案標籤。
- 保留業主端必要的版本辨識。
- 驗收資料不得使用會讓正式客戶困惑的內部文案。

## 4. AI 入口位置與額度風險

### 問題

AI 入口太靠前，容易讓客人誤以為必須先使用 AI；若頁面載入時自動呼叫會浪費額度。

### 處理

- AI 區塊移到主要預約按鈕之後。
- 只有客人按下「取得 AI 建議」才呼叫 API。
- 標準版在前端能力查詢前即停止。

## 5. Wrangler migration 追蹤與實際 schema 不一致

### 問題

`0014` 曾以單檔 SQL 套用，實際 schema 與 `schema_versions` 已存在，但 Wrangler 的 `d1_migrations` 沒有紀錄，因此 `migrations list` 誤判 `0014`、`0015` 都待套用。若直接執行整批 apply，可能重複 ALTER COLUMN 並失敗。

### 處理

1. 先匯出完整 D1 備份。
2. 唯讀確認 `0014` schema version 與欄位確實存在。
3. 只執行 `0015` 單檔 SQL。
4. 驗證 `0015` 四個欄位與外鍵。
5. 在條件確認 schema 存在後，補登 `0014`、`0015` 到 `d1_migrations`。
6. 最後確認 `No migrations to apply`。

### 後續注意

未來 migration 應優先使用 Wrangler migration apply；若必須單檔執行，必須同步處理 migration tracking。

## 6. 瀏覽器頁籤仍載入舊版 JavaScript

### 問題

Pages 部署後使用部署前已開啟的 LIFF 頁籤驗收，頁籤仍載入舊版 JS，第一次點擊直接建立了測試預約，沒有顯示新增的追加提醒。

### 處理

- 立即以正常客戶取消流程取消測試預約並釋放時段。
- D1 唯讀確認該筆狀態為 `cancelled_by_customer`。
- 強制重新載入後，確認載入 `app.js?v=20260724005`。
- 再次驗收，確認追加提醒与預約前問卷出現。
- 比對遠端與本機 app.js SHA-256 完全一致。

### 後續注意

每次 Pages 部署後，遠端驗收前必須：

1. 確認 HTML cache-busting 版本。
2. 重新載入頁籤。
3. 檢查實際載入的 script URL。
4. 再進行會產生遠端資料的操作。

## 7. 遠端測試資料清理

### 原則

- 驗收若建立預約，必須記錄日期、時間與 booking ID。
- 測試完成立即取消或清理。
- 再從 D1 查核狀態與外鍵。
- 不使用 production。

## 8. 前端副本與快取

### 問題

客戶端／業主端各有來源目錄與 Pages `docs` 副本，若只改一份會造成部署版本不同；手機 LIFF 也可能繼續使用舊 cache。

### 處理

- 每次修改後比較來源與 docs 副本。
- 更新 script query cache-busting。
- 自動測試檢查副本一致性。
- 部署後比對遠端檔案雜湊。
